Report 02 / Architecture and implementation

Modular System Specification

One authoritative AssetStudio backend, capability-based GPU nodes, and a native MacBook Blender companion.
THREE DEPLOYABLE ROLESFIRST-CLASS .BLENDMULTI-NODE EXECUTION30 September 2026
User decisions, recommendations, implementation facts and unverified video claims are kept distinct.

1. Executive specification

Distribute execution across machines. Keep plans, review, source history and publication under one AssetStudio authority.

The target system has three independently deployable roles: a Studio backend with web UI, one or more Linux compute nodes, and a native MacBook companion that runs Blender authoring sessions using Claude Code or Codex. Keep the main application a modular backend rather than turning every feature into a microservice.

Studio

Owns projects, frozen plans, jobs, review, source revisions, publication and execution assignments. No GPU or model weights required.

Compute nodes

Own model installations, engine runtimes, local device admission, input caches and durable result spools. Scale independent work across machines.

MacBook companion

Owns local workspaces, agent adapters, Blender session control, human takeover, coherent checkpoints and result submission.

Specification status

This is a consolidated target specification and implementation guide. It records user decisions, recommended technical choices and unresolved design points separately. It is not a claim that the described services, APIs or authoring lifecycle are already implemented.

Proposed architecture choices

Use one backend authority initially. Register capability-reporting compute nodes and one MacBook companion. Let nodes connect outward over authenticated HTTPS. Retain separate ComfyUI/aux/TRELLIS runtimes behind a node agent. Use content-addressed immutable artifacts and exact input/review bindings. Keep provider credentials on the MacBook. Start with ordinary APIs and a durable backend journal, not a mandatory broker or cluster orchestrator.

Non-goals for v1

Do not build a general-purpose 3D editor in the browser, a replacement coding IDE, a full embedded LLM platform, an automatic binary .blend merge engine or a second terrain editor. Do not require S3, Kubernetes, Redis, a workflow engine or multiple active backend replicas simply to support several execution nodes.

AI-video motion reconstruction, arbitrary creature rigging, cloud Blender desktops, multi-GPU execution of a single model and multi-output kit publication are separate extensions. The architecture should not prevent them, but they are not implicit v1 promises.

Studio backend and UI

Studio owns all product decisions: project and category schema, style/reference bindings, plans, job membership, review gates, source records, artifact metadata, current-version pointers and delivery plans. It also owns assignment and accepted execution state.

The backend must serve planning and the library without a GPU machine or MacBook being online. Expensive previews or validation must not block ordinary API requests. Use a bounded local processing pool initially, with the option to dispatch heavier work to a node later.

Keep the web UI served with the backend in v1. Logical frontend/API boundaries do not require separate deployments. A reverse proxy can provide TLS and routing without introducing a second product-state authority.

Linux compute-node agent

Use one node-control process per physical compute machine. It reports identity, capabilities, model inventory, device inventory, software versions and local health. It accepts assigned attempts, manages local physical-device admission and adapts the existing engine runtimes.

Retain ComfyUI, auxiliary models and TRELLIS as separate runtimes/containers where appropriate. The node agent need not import all their dependencies. It controls them through explicit adapters and verifies supported protocols.

The node stores caches, durable execution state and unacknowledged outputs. It does not mutate project manifests, approve QA or publish asset versions directly.

MacBook companion

The companion is a native execution controller with a CLI first and an optional menu-bar interface later. It materializes workspaces, launches the local agent application, binds it to the right Blender session, collects checkpoints and submits evidence.

The user can watch Blender and explicitly take over. Managed authoring must not become a hidden background editor of whichever .blend happens to be open. Bind each session to a project, job, workspace, primary file and Blender process identity.

Storage role

Canonical artifact storage can initially be local to the main server. It is a logical service boundary, not necessarily a separate deployable process. Worker caches are replaceable; acknowledged canonical artifacts and their metadata are not.

A future object store can handle large transfers. It does not replace the publication transaction or the source manifest. Keep storage operations behind the existing repository abstraction.

Physical hosting remains open

The recommended deployment is backend/storage on an always-on server, Linux inference on the GPU workstation, and authoring on the MacBook. Hosting the backend and compute node on the same Linux machine is also valid initially. The user has not selected the backend's physical placement. Preserve that as a deployment option.

6. User journeys and workflow types

Journey A: plan → manual Blender handoff

Create or select a planned asset. Choose from-scratch or an exact starting source/generated artifact. Freeze an authoring plan with its references, requirements and review gates. Export a folder/ZIP handoff containing the plan, source, dependency manifest and instructions.

The user opens the package on the MacBook with Claude Code or Codex, using the companion/CLI for context and checkpoint submission. Manual mode does not mean manually editing backend JSON. Submitted work follows the same validation, review and publication rules as managed mode.

Journey B: managed authoring

The user selects “Start in Blender” and a provider. Studio records a durable assignment for the paired MacBook. The companion receives it over its outbound connection, checks compatibility and permissions, materializes a workspace, then launches the local provider and Blender session.

The browser does not execute shell commands or need a direct incoming connection to the MacBook. Progress and review requests return through Studio. If the companion is unavailable, the UI shows the reason and retains the queued intent; it does not silently launch elsewhere.

Journey C: generated geometry → Blender refinement

Existing generation remains available: approved reference/candidate → segmentation → TRELLIS sampling → raw intermediate → export/validation. Create an authoring job bound to a selected output or source revision. Preserve its generated origin and exact upstream model/workflow receipts.

Blender may then remodel, retopologize, paint, rig or animate. A refine job does not overwrite the generated artifact and does not pretend the output is still a pure inference result.

Journey D: revise an existing asset

Choose exact asset/version/source revision, create a new authoring plan and workspace, then submit a child source revision. A concurrent new publication causes an explicit conflict at promotion. Retain both histories; no silent “last writer wins.”

Journey E: variants and families

A new visual/structural variant is a new asset in the family, bound to its source version and requested changes. A repair to the same intended asset is a new version. Both paths may use Blender, but they must not be confused by the agent.

Workflow model

Introduce a discriminated workflow kind, conceptually generation, blender_authoring, deterministic_transform and the existing reviewed-import path. Do not keep adding boolean exceptions beside Job.direct. Preserve existing generation history and compatibility readers.

New UI jobs should continue the selected one-job/one-asset direction. Existing records that support several items must remain readable; do not silently split historical IDs and break their receipts. Separate workflow stages from the transport used to execute them. R1 R12

7. Planning, style and media references

The domain must support an immutable plan regardless of whether the user writes it through a form, chat assistant or Markdown/YAML editor. Keep the planning UI open. The initial implementation can use a simple form and a readable plan preview without making that the permanent product decision.

Authoring-plan content

Record intended asset/variant, workflow, source revision, technical requirements, advisory budgets, material/rig profiles, animation requests, outputs, references, style snapshot, gate policy and external-data permissions. Each requirement needs an identity and a declared enforcement level: machine-checked, advisory, human-reviewed or unsupported.

AI planning suggestions must never overwrite manual requirements silently. Freeze only after the chosen authorization step. Editing a frozen plan creates a new revision and invalidates incompatible downstream approvals.

Reference semantics

Reuse existing Media Library guidance images. Bind their artifact IDs and hashes, not only mutable display metadata. A soft-archived reference may be ineligible for new plans while remaining available as immutable evidence for an already frozen plan, subject to the retention policy.

A reference set should label shape, proportion, palette, material, motion or detail roles and identify which references are authoritative. Prompt enhancement must preserve those constraints or surface a conflict. Conservative/creative enhancement choices can remain part of the plan without granting broader execution permissions.

The current Media Library's image-only boundary is separate from a future motion-reference store. Do not accept arbitrary video or .blend uploads through an image endpoint merely to reuse its UI. R1 R16

Project-specific versus reusable profiles

The product stays general. A medieval style, humanoid skeleton and Terrain3D export profile are selected project resources—not hard-coded branches in the backend. Store profile revisions and dependency hashes so an agent cannot accidentally use a new rig/material definition mid-job.

Identity rules

A logical task describes the requested operation on exact inputs. A retry creates a new attempt when the previous computation was lost or explicitly restarted. A repeated delivery of the same attempt must be recognized rather than treated as a new computation.

Do not use filenames or provider conversation IDs as asset identities. Provider session IDs are adapter metadata. Local paths are locations, not revision identities. A source revision is identified by an immutable manifest digest or an immutable ID bound to that digest.

Keep project/job/item identities compatible with the existing library. A new authoring record must reference existing objects rather than creating an unrelated shadow asset universe.

9. First-class Blender source support

Source support is broader than a .blend upload

AssetStudio must recognize, store, version, restore, inspect and hand off .blend sources. It must show source state even when an export is unavailable. It must preserve the dependencies needed for meaningful reopening and warn about unresolved or unsupported dependencies.

A valid stored source does not need to be a game-ready asset. Import inspection may be pending or limited while raw source preservation succeeds. Display these states separately and never equate “stored” with “safe to execute” or “fully validated.”

Source and delivery contracts

Extend artifact contracts intentionally. The current model3d role set cannot express editable source packages. Avoid bypassing the contract by putting arbitrary file maps into an untyped meta field. R2

Recommended design: separate source acceptance and delivery profiles. A Blender-authored asset version may point to an accepted source revision and optionally one or more validated exports. A delivery profile requiring GLB cannot be satisfied by source alone. Existing model-only imported/generated versions remain valid legacy/delivery records.

A new source may be checkpointed without publication. An accepted source-only milestone may become an asset version with explicit “export pending” readiness; it must not displace the game's last delivered artifact automatically. Keep accepted-library state and delivery receipts separate.

Package policy

Use one primary .blend entry point per source revision. A package can include multiple objects, rigs, actions and linked dependencies. Whether one kit publishes into several independent assets is still open and must be modeled explicitly later.

Allow packed or externally stored resources when supported by the selected profile. Do not assume packing captures every possible dependency. Inspection must find textures, linked libraries and any required cache/resource paths. Record approved add-ons by version; never silently install code because a source requests it. B2

Dependency closure

A source manifest must list the required files and their relative paths. Resolve dependencies only within explicitly allowed roots. Detect missing paths, out-of-package references and collisions caused by case-insensitive filesystems. Reject path traversal, absolute-path archive entries, unsafe links and Unicode/case collisions that would materialize ambiguously.

A user can explicitly add a required file to the package. The runner must not search the whole MacBook and upload unrelated directories while trying to repair a dependency.

Clean restore test

Materialize the package into an empty directory, using verified bytes. Open it with the supported Blender build and declared add-ons under the chosen execution policy. Inspect expected scene objects/resources and produce a preview/export where required. Report missing dependencies and compatibility limits explicitly.

A successful clean restore demonstrates portability under that tested toolchain. It does not prove the file is safe in every Blender version or that a future exporter will produce identical bytes.

Five distinct operations

Operation Persistence and authority
Workspace save Mutable working state on the MacBook.
Local autosave Recovery-only data; not a canonical source revision until explicitly ingested.
Checkpoint Immutable source snapshot and metadata acknowledged by Studio.
Submission/publication Frozen proposal followed by authorized review and asset-version publication.
Delivery Explicit application of a frozen export plan to the Godot test target.

Checkpoint transaction

Stop admission of new mutations and drain the active operation. Save the scene and required modified resources. Build a stable snapshot in a separate staging directory. Hash files from that snapshot, not from paths that Blender can still rewrite. Upload only missing blobs, then submit the manifest for verification and immutable commit.

Return a durable receipt before deleting staging or considering the checkpoint remotely safe. If saving an image or dependency fails, report an incomplete checkpoint; do not claim the last .blend timestamp proves coherence.

A filesystem watcher may detect dirty state, but it must not be the publication protocol. Keep export and review evidence tied to the exact checkpoint digest.

Human takeover protocol

Mermaid source
flowchart LR
  A[Agent owns workspace] --> D[Stop admission and drain mutation]
  D --> C[Checkpoint and fence old generation]
  C --> H[Human owns workspace]
  H --> S[Save and checkpoint, refresh scene inventory]
  S --> R[Explicit agent resume under new generation]

The companion stops new agent commands, waits for or explicitly interrupts the in-flight operation, checkpoints and increments/fences the workspace generation. The old provider cannot continue mutating after control transfers.

During manual editing, preserve local autosave and a visible ownership indicator. To resume, the user saves/checkpoints, the companion refreshes scene inventory, and a provider receives the new authoritative state. Conversation history can assist context but must not replace inspection.

If an operation cannot be safely drained, show “takeover pending” rather than admitting a second writer. Force interruption is an explicit recovery action with a potentially uncertain scene state; restore a checkpoint when necessary.

Concurrency and conflicts

Different assets/workspaces may run concurrently. Alternative explorations of one source use separate workspaces and child revisions. No automatic .blend merge is promised.

At promotion, compare the expected base/current version and submission binding. A stale submission remains preserved, but cannot silently overwrite a newer accepted version. Allow an explicit new-version/rebase-by-authoring decision or a separately named variant where appropriate.

11. Compute nodes and multi-GPU scheduling

Machines, devices and engines

A node is a machine-level execution environment. A device is a physical resource or an explicitly modeled partition. An engine runtime offers capabilities on one or more devices. A task attempt consumes a declared resource set.

Identify a GPU with a stable node/device identity, not a global gpu0 string. Two machines can each have device index 0. Two containers on the same GPU must map to one physical resource and one admission authority.

For NVIDIA machines, collect physical UUIDs where available and record the mapping to runtime-visible devices. Treat partitioned or multi-device configurations as explicit resource models. Do not infer capacity by counting endpoints.

Node inventory

A capability advertisement should include operation/contract versions, engine identity, verified model revisions, supported export modes, platform/architecture, device memory/capacity and current loaded-model state. Include observation timestamps and freshness. A stale heartbeat is not current capacity.

Readiness means a compatible authorized node has a verified supported installation; immediate schedulability also depends on current reservations and health. Keep “installed,” “loaded,” “ready,” “busy,” “unreachable” and “unknown” distinct.

Model verification moves to the node

Remove the backend requirement to mount model weights. Studio keeps the desired model/profile catalog and pinned identities. The node verifies its local artifacts against that catalog and reports inventory/verification receipts. Do not accept an unversioned “model installed” boolean as reproducibility evidence.

A recipe can be ready on one node and unavailable on another. Select compatible nodes without silently substituting a model revision or exporter. Keep explicit installation/download commands outside normal job dispatch; production tasks should not trigger surprise multi-gigabyte downloads.

Central placement, local admission

The central scheduler chooses eligible tasks, node placement and priority. The node decides whether the physical resource can be admitted now and performs unload/drain where required. Preserve the existing safety concept that unknown ownership prevents dispatch. R7

The node does not independently advance product gates or invent follow-up stages. It executes authorized attempts and reports observations. Studio commits outcomes and makes downstream work ready.

Matching and optimization

Hard matching constraints Soft placement preferences
Operation and protocol compatibility Required model already loaded
Exact model/runtime/profile identity Input artifacts already cached
Authorized project and data policy Short queue and predicted completion
Sufficient memory/device requirements Fewer expensive model switches
Healthy resource ownership Fairness and priority across users/jobs

Preserve stage-first/model-aware scheduling: group compatible operations across jobs where that saves load time. Do not let warm-model preference starve other work. Keep limits for pass length and waiting time configurable and measured, not guessed universal constants.

Resource granularity

A Blender authoring session owns a workspace, not a remote GPU for its entire lifetime. A render/bake or VLM review may request compute separately. Release unnecessary reservations before waiting at a review gate or asking another service for work.

Avoid the deadlock where an authoring stage holds the only GPU while waiting for QA on the same device. More generally, do not hold one scarce resource while synchronously waiting for another without an explicit reservation/order policy.

Parallelism limits

Default to one heavy inference execution per physical GPU until a tested profile permits safe concurrency. Multiple GPUs improve throughput across independent tasks. They do not automatically pool VRAM for one model. Multi-device inference requires its own capability, scheduler semantics and acceptance tests.

Record capacity estimates and actual peaks separately. Memory reported free is not a guarantee that an arbitrary model run fits. Handle out-of-memory as an execution/resource event with bounded retry or an explicit smaller/different approved profile.

12. Worker protocol, transport and execution contracts

Outbound connections

Compute nodes and the MacBook companion initiate authenticated HTTPS connections to Studio. Start with durable API commands and long-poll assignment retrieval. Optional event streams improve responsiveness but must not become the only source of truth.

A disconnection can lose transient status notifications. Reconnect with an event cursor or fetch a current projection from durable state. Duplicate or reordered events must not roll an execution backward. The browser can use the existing event approach as a view over durable records.

Keep large artifact transfer separate from control messages. Do not embed .blend files, raw meshes or image bundles in status events. Remote nodes receive artifact IDs/hashes and scoped fetch/upload authorization, not arbitrary backend filesystem paths.

Version negotiation

Negotiate node-protocol versions and capability/operation versions at registration. Refuse incompatible work with an actionable explanation. Freeze the selected versions on an execution attempt. A node upgrade may change its inventory, but must not mutate the identity of a running or accepted attempt.

Use typed request/response schemas and generated frontend/runner clients where practical. The earlier code review identified handwritten frontend response types as a maintenance risk; extending distributed contracts without schema generation would increase that risk.

13. Durable execution, leases and recovery

Mermaid source
flowchart LR
  Q[Queued task and frozen input digest] --> L[Leased attempt with node and generation]
  L --> A[Node admission and physical-device lease]
  A --> X[Execute and durably spool result]
  X --> U[Upload and verify immutable artifacts]
  U --> C[Commit accepted result and downstream state]
  C --> R[Return durable receipt before spool cleanup]

Logical task versus attempt

A logical task represents an operation on exact inputs. Each computation attempt has its own ID and assignment generation. Delivering the same attempt message twice must reconcile against local durable execution state. Explicit retry after lost execution creates a new attempt; it must not change the old attempt's history.

Exactly-once delivery/computation is not a realistic assumption across network failures. The requirement is replay-safe submission, verified ingestion and non-duplicated accepted publication. Duplicate computation may occur during exceptional recovery, but its effects must remain isolated and attributable.

Proposed execution and authoring state models

Keep workflow state separate from connectivity and control intent. A disconnected node does not make its result failed, and a paused workflow does not prove that an in-flight computation has stopped. Persist transitions conditionally against the prior revision and owner generation.

Record Proposed progression Important rule
Logical task queued → assigned → running → result pending → succeeded Dependencies unlock only after the result is verified and durably committed. Failure/cancellation/blocked states carry reasons and retry policy.
Task attempt leased → admitted → executing → spooled → ingesting → committed Lost or failed attempts remain historical. A retry creates a new attempt instead of erasing the prior one.
Authoring plan draft → frozen → superseded Frozen plans are immutable. Changed requirements create a successor with a new digest.
Authoring session preparing → active → waiting for review → active or completed Paused, failed and cancelled outcomes are explicit. Completed means the assigned work ended, not that the asset was published.
Submission submitted → validating → ready for review → accepted or changes requested Acceptance binds the exact source/export/evidence set. Later corrections create a new submission.
Delivery plan planned → authorized → applying → completed or partially failed Retry only the recorded managed outputs. Never widen the destination scope after authorization.

Use independent fields for connection health (online, stale, disconnected), requested control (run, pause, cancel) and workspace owner (agent, human, unassigned). Exact enum spellings are proposed; finalize them with the typed protocol. The behavior above is the design contract.

If a review gate changes from optional to required during a session, record a new policy revision and require explicit authorization for its application. Do not silently invalidate past accepted history or authorize new stages using a policy the operator has not seen.

Lease semantics

Use separate concepts for central assignment/workspace ownership and local physical-device leases. Both need stable identities and fencing generations, but their expiration policies differ.

A compute assignment losing contact becomes uncertain. The node stops admitting new unauthorized work. Existing work may finish into a local spool if policy permits, but it cannot force acceptance into Studio. A late result needs matching attempt/generation and reconciliation policy.

A MacBook authoring session losing contact must not automatically migrate to another writer. Preserve local state and mark disconnected. New product-stage progression pauses according to offline policy. The companion can keep recovery data without claiming remote acceptance.

Fencing stale work

The backend rejects stale attempt generations. The Blender bridge must also reject stale workspace generations at the mutation boundary, not only when uploading the final result. Otherwise an old agent could continue editing after takeover even if it cannot publish.

A lease is not a process kill. Do not declare a GPU idle merely because a central timer expired. Require local drain/stop confirmation or explicit operator recovery. Retain the existing epoch-and-acknowledgement principle when extracting node-local ownership. R7

Result commit sequence

Write outputs into the worker spool, build an immutable result manifest and report the outcome. Studio stages and verifies blobs, checks the input/profile/generation bindings, then commits accepted execution outcome and required downstream scheduling state through its durable journal mechanism. Return an ingestion receipt only after the necessary records are durable.

Where canonical project records and the journal are separate stores, do not claim a single distributed transaction. Use durable command intents, derived IDs, conditional commits and replay/reconciliation. The existing publication design provides a useful model: the manifest update is the publication point and receipts make retries discover the same outcome. R8

Recovery matrix

Incident Required behavior
Duplicate assignment Reuse/reconcile the same local attempt; do not start a second execution.
Backend restart during a run Reconstruct assignments from durable state and reconcile node receipts.
Node restart after output was spooled Recover local execution and upload the preserved output.

Retries must be bounded and classified. Retrying an invalid mesh or permission refusal indefinitely does not improve reliability. Keep automatic retry settings configurable and explicit retry distinguishable from automated attempts.

14. Artifact transfer, caching and source storage

Content addressing and file manifests

Store immutable bytes by hash and preserve role/provenance separately. A source revision is a path-to-artifact manifest with one primary .blend entry point. This allows unchanged textures or dependencies to be reused across revisions without repeatedly uploading them.

Whole-file deduplication does not provide binary deltas for a changed .blend. Start with full-file blobs and measure growth. Chunk-level deduplication can be added later without changing the concept of an immutable source revision.

Streaming and resumable transfer

Do not extend a small image-upload handler by simply raising its limit and loading a huge source bundle into memory. Support bounded streaming and a staged transfer protocol. Validate declared and actual size, hash, role and project authorization. Define limits per file, package, decoded media and aggregate workspace.

Use a resumable strategy with verified ranges/chunks where justified, but always verify the final complete file before commit. Do not trust client-provided hash text without checking bytes. Interrupted or abandoned upload sessions are garbage-collection candidates, not published artifacts.

Cache behavior

Cache inputs by immutable digest on each node. Report cache presence as a scheduling hint, not proof of integrity. Verify on materialization according to the storage policy. Eviction may remove reconstructible caches, but not the only copy of unacknowledged outputs or an active dirty workspace.

Workers need not share an NFS mount. Fetch missing input blobs through authenticated transfer, then operate on local copies. A future shared/object store can optimize transport while preserving the same contracts.

Writable materialization

Never expose canonical blobs as writable hard links in a Blender workspace. Use an independent writable copy or a correctly implemented copy-on-write mechanism. Editing a source must not alter a previously accepted revision.

Materialize into a staging directory, check paths and hashes, then make the completed workspace visible. Distinguish user-editable source from generated delivery files and temporary inspection output.

Retention classes

Preserve accepted source versions and referenced dependencies. Keep named checkpoints according to project policy. Use a shorter explicit policy for local autosaves, candidate renders, logs and abandoned transfers. Raw TRELLIS intermediates can remain valuable for re-export, but their retention needs separate budgeting.

Never let generic cache cleanup remove data needed by a published version or an active session. Begin retention/GC with a dry-run plan and reachable-reference analysis. Publication history must not become invalid after a cleanup pass.

Portable projects and backups

Back up project configuration, manifests, source revisions, artifact records, blobs and the execution journal needed for recovery. A blob backup without the manifests is not enough. A journal backup taken at an unrelated time can require reconciliation.

Provide a coherent snapshot procedure, integrity verification and restore test. Stop new admissions or record a clear snapshot barrier while capturing related state. Rebuildable search indexes can be regenerated; canonical records and unacknowledged work must not be assumed reconstructible.

15. MacBook companion and Blender bridge

Companion responsibilities

The companion pairs with Studio, stores scoped node credentials locally, advertises installed Blender/provider/tool versions and receives only authorized work. It manages workspace paths, local manifests, process identities, checkpoint staging and upload receipts.

It should show which project/job/source is open, who owns mutation rights, what remains unsynced and whether Studio is reachable. A CLI first is sufficient for v1; an optional menu-bar application can add visibility and launch controls without duplicating the whole web UI.

The companion implementation language is not decided. Reuse the project's existing expertise and supported provider interfaces. Do not require rewriting the backend in a new language or shipping CUDA/PyTorch in the MacBook application.

Blender bridge

The bridge provides scene inspection, approved mutation operations, file save/checkpoint hooks, dependency inventory, rendering, export and validation. Main-thread scene mutations are serialized and checked against the workspace generation. Heavy network/provider work must not block Blender's UI thread.

Return structured outcomes with operation ID, scene/workspace identity, affected objects, warnings and output artifact locations. Large files flow through the companion's artifact channel rather than being embedded in MCP messages.

Use the community MCP integration as a version-pinned starting point where it fits. Its Python execution support is powerful but does not provide product-state ownership, publication controls or a complete sandbox. D8

Tool strategy

Provide stable tools for repetitive boundaries: inspect scene, capture views, validate source, save a coherent checkpoint, collect dependencies and export with a profile. Allow scoped exploratory scripts for creative work. Promote repeated successful scripts to reviewed tooling rather than regenerating them every session.

An integration cannot guarantee idempotence for arbitrary scene scripts. For risky operations, use precondition checks, operation receipts and before/after checkpoints. Restrict arbitrary code according to user policy rather than pretending a text filter makes Python execution safe.

Session selection

Bind a runner to a specific Blender instance and entry file. Do not connect to the first open socket and assume it belongs to the requested job. Detect changed files/processes, unexpected scene resets and stale workspace identity before applying commands.

For parallel sessions, use separate workspaces and explicit Blender process identities. The v1 default should be one interactive mutation session on the MacBook, with resource limits for background exports/reviews.

16. Claude Code and Codex provider adapters

Provider-neutral product contract

Both adapters need to start a session, send a task, surface progress and permission requests, report completion/failure, and support interruption/resumption to the extent the provider actually exposes it. Normalize product events without discarding provider-specific diagnostics.

Store provider session IDs and available usage information as provenance. Do not make them the authoritative source revision or task identity. A completed chat turn does not mean a valid asset was submitted.

Supported integration surfaces

Claude Code documents programmatic execution, including structured JSON/streaming output. Codex documents non-interactive execution and App Server integration with local stdio. Use those supported surfaces rather than scraping terminal text. Pin schemas and test the exact installed versions. D10 D12 D13

Recommended evaluation: a structured Claude Code interface for initial managed runs, with SDK use if interaction needs justify it; Codex App Server over local stdio for rich managed sessions, with non-interactive execution for bounded tasks. This is an integration recommendation, not a frozen choice of provider API version.

Permissions and credentials

Keep provider credentials on the MacBook in supported local authentication facilities. Do not put tokens into asset packages, logs, generated scripts or backend project records. Do not extract hidden credential caches or bypass provider access policies.

Separate local application execution from hosted model inference. The user selected Claude Code and Codex, but the scope of allowed outbound asset data remains open. Two approval layers

Use an independent review context when useful, but keep default orchestration economical. Separate logical authoring, critique and integration responsibilities without automatically launching four costly agents for every small prop.

17. Security and trust boundaries

Threat model

The initial deployment is a trusted operator with paired personal machines, not an anonymous multi-tenant render farm. Nevertheless, arbitrary scripts, uploaded source files, external references and network failures create real boundaries. The system must not rely on “local network” as authorization.

The earlier backend used a custom mutation header and origin check appropriate to its loopback-oriented posture. That is CSRF protection, not authenticated remote node identity or per-job authorization. Add real node credentials and scoped permissions before exposing remote execution.

Pairing and network access

Use a user-confirmed pairing flow with a short-lived enrollment secret, a stable node identity and revocable credentials. Require authenticated TLS for remote control/transfer. A private VPN or trusted reverse proxy may simplify access, but does not remove application authorization.

Keep Blender's scene-control socket local to the MacBook. The community bridge documentation warns about unauthenticated/unencrypted local socket exposure. Do not publish that endpoint directly to the network. D8

Least privilege

A node can read assigned inputs, upload designated outputs and report status. It cannot approve gates, read every project, mutate source records directly, choose arbitrary target directories or push to Git. A companion should not gain access to unrelated home-directory data merely because it runs under the user's account.

Restrict download URLs and artifact access to intended project/attempt scope. Do not allow agents to turn an artifact-fetch tool into unrestricted server-side URL fetching. Short-lived transfer links need expiry and purpose binding.

Blender source is executable-adjacent content

Treat scripts, drivers, linked libraries and add-ons as untrusted unless explicitly approved. Disable automatic script execution for inspection where possible and document what this prevents. That setting is not a complete sandbox against parser vulnerabilities, malicious add-ons or code explicitly executed through MCP. B3

Inspect unfamiliar sources in a restricted execution environment with resource limits, minimal filesystem access and controlled network policy. If required functionality depends on blocked code, report it and request the appropriate permission rather than silently enabling everything.

Prompt injection and external references

Reference images, readme files, imported metadata and comments are task data. They do not grant permission to install software, read secrets or change the plan. Agents should identify conflicting instructions in untrusted inputs and continue under the frozen policy.

The agent's shell sandbox does not automatically confine a separate Blender process reached through MCP. Enforce restrictions at the actual execution/process boundary. Claude's security documentation also treats MCP server trust and permissions as explicit concerns. D11

Upload and archive safety

Check path containment, symlinks, absolute paths, duplicate normalized names, expansion ratios and aggregate sizes before materialization. Parse/inspect in constrained processes where warranted. Reject unsupported files clearly. A clean hash proves identity, not safety or licensing.

Redact credentials and sensitive paths from routine logs. Keep audit records for permission grants, source access, human takeover, overrides and publication. No hidden telemetry is required for the architecture.

19. Godot, Terrain3D and delivery

Authored source versus runtime output

Blender remains the authoring source. Use a pinned GLB export profile as the normal reviewed game-delivery artifact. Godot also supports direct .blend import through Blender, which may be useful for local iteration; that convenience must not bypass source history or the reviewed delivery contract. D1

Godot owns animation state transitions, runtime blending, gameplay behavior and world placement. Blender owns authored clips. The AnimationTree/AnimationPlayer distinction should be reflected in the test-project wrapper rather than attempting to reproduce the whole game inside the source asset. D4

Delivery plan

Freeze selected asset versions, export hashes, output paths, target profile and wrapper metadata before writing. Show collisions and intended updates. Write only owned/generated files. Preserve hand-authored .tscn wrappers, project configuration and unrelated assets.

Use staging and atomic per-file replacement where available, then write a durable delivery receipt. Retry should inspect the receipt and hashes, not duplicate names or overwrite changes made after the plan. Removing old generated files requires an explicit owned-file manifest and policy, not a broad directory deletion.

20. Backend persistence, modularity and scaling

One backend, many workers

Several compute nodes do not require several backend replicas. Begin with one active Studio process/authority, a durable journal on its machine and canonical project/artifact storage. Keep the single-writer/publication model understandable.

Retain the distinction between canonical portable project records and the execution journal. Search indexes are derived caches; they must not become an accidental second authority for version identity or publication.

SQLite and local persistence

A single-backend deployment can retain SQLite where appropriate. Workers access APIs, not database files. Do not share a live WAL database across machines through a network filesystem: SQLite documents the same-host requirement. D14

Backend backup and restore must include enough journal state to reconcile active/uncertain executions. The node spool is an additional recovery source, not a substitute for the canonical backend record.

When to add infrastructure

Consider an external object store when artifact capacity or transfer patterns justify it. Consider a broker when durable event fan-out or scale requires it. Consider a different transactional database and scheduler-leader design when multiple active backend instances are genuinely needed.

None of these changes follows automatically from “add a second GPU node.” Do not add infrastructure to compensate for undefined ownership or missing idempotency.

21. UI requirements without freezing the planning interface

The interface should make task, source and delivery state visible without requiring the user to understand worker internals.

Planning and job view

Show the brief, references, selected source, proposed outputs, gate policy and provider/runner choice. Preserve an editable draft and an explicit frozen plan. Display unsupported requirements and style/reference conflicts before execution.

Offer both Download handoff and Start on MacBook. Explain when the MacBook or required toolchain is unavailable. A saved job is not automatically authorized to run inference or external agent calls.

Authoring workspace view

Show the active writer, provider, Blender/tool versions, current source revision, last local/remote checkpoint, dirty/unsynced state, active operation and review gate. Provide pause, takeover, resume, checkpoint and submit actions with clear preconditions.

Do not show a fake percentage when there is no measurable denominator. Use stage/status and actual elapsed work. Surface “waiting for human,” “disconnected” and “uncertain operation” distinctly.

Asset and source view

22. Observability, performance and operating limits

Traceability

Use project, job, task, attempt, session, source revision, submission and publication IDs consistently in logs/events. Correlate a visible asset version to its source and execution receipts. Preserve error categories rather than returning generic “failed” for every incident.

Metrics

Track queue time, local preparation, model load time, execution, upload, validation and human waiting separately. Track resource peaks, retries, lost/uncertain attempts, duplicate messages, cache hits and failed restoration. For authoring, record milestone count, correction cycles and accepted-output rate.

Provider tokens/cost are recorded only when available, with measurement source and provider/model identity. Missing values remain null/unavailable, not zero. Do not infer current billing rules or subscription entitlements from the fact that a CLI is installed.

Limits

Bound upload/package sizes, archive expansion, image dimensions, memory use, execution duration, provider iterations, concurrent sessions and log retention. Keep limits profile-specific and testable. Do not copy example values from a report into universal production limits without measurement.

A production task cannot silently download a new model, install an add-on, increase external budget or switch a provider to recover from failure. These require explicit policy authorization.

Offline states

Distinguish offline library access, offline local inference and local agent application with hosted inference. They are different properties. Library-only mode must still support source browsing, manual handoff preparation and preserved review history without GPU workers.

The default proposal is to pause new autonomous authoring progression when backend authorization cannot be renewed, while preserving local recovery. Continued offline authoring is an open policy decision; support eventual reconciliation without claiming offline work was remotely approved.

24. Migration and implementation plan

Phase 0 — Baseline and contract audit

Pin the implementation baseline and compare it with this report's source references. Run existing backend/frontend tests and capture actual results. Inventory current IDs, storage contracts, receipts, model profiles, media references and frontend API shapes. Address the malformed-GLB test cases without presenting that as a complete audit.

Preserve newer review/run/provenance hardening and Media Library behavior. Avoid reintroducing the older acceptance-binding or readiness weaknesses while extracting execution.

Phase 1 — Protocol and node registry

Create typed node, attempt, capability, inventory and transfer contracts. Add registration/revocation, durable assignment and simulated-node tests. Define single-backend ownership and database boundaries. Demonstrate two nodes with identical local GPU indices and incompatible model revisions.

Keep a compatibility adapter for the existing local deployment so the product remains usable during extraction. Do not migrate all engine code and authoring UI in one untestable change.

Phase 2 — Extract Linux compute control

Move verified model inventory and physical-device admission to the compute node. Adapt ComfyUI/aux/TRELLIS through existing interfaces. Preserve result spooling, cancellation, epochs and exact model/workflow receipts. Run Studio with no model-weight mount as the acceptance target.

Prove one remote node before optimizing multiple nodes. Then add capability-based placement, cache/residency preference and fairness, with failure-injection tests for disconnect/restart.

Phase 3 — First-class source lifecycle and manual round trip

Implement source-package upload, dependency manifest, immutable source revision, restoration and source-only asset state. Add handoff packages and manual submission before managed agent launch. Prove that an edited source can return, be reviewed and reopen elsewhere without the original MacBook paths.

Extend publication contracts by schema/profile, not by disabling existing role checks. Keep legacy model-only versions valid. Add retention reachability and restore tests before relying on a large source library.

Phase 4 — MacBook companion and Blender bridge

Implement pairing, local workspace/process binding, serialized mutation, coherent checkpointing, local spool and explicit takeover. Start with one interactive session and a small versioned tool set. Test sleep, agent interruption and Blender crash recovery.

Phase 5 — Claude Code and Codex adapters

Integrate each provider through a supported structured interface. Implement normalized events, permission prompts, bounded runs, reference-data policy and identical submission contracts. Preserve manual mode. Validate provider capabilities independently and document limitations.

Phase 6 — Review and Godot delivery

Add source/dependency views, animation controls, validation reports and exact-bound gates. Implement export plans, file/package delivery and the isolated Godot test target. Preserve hand-authored wrappers and forbid main-game writes by default.

Phase 7 — Animation profile and scale hardening

Complete the articulated-object slice, then one humanoid profile with retargeting/contact/loop checks. Profile artifact transfer, memory, storage growth, multi-node fairness and provider cost. Only then decide whether object storage, chunk deduplication or richer orchestration is justified.

Migration rules

Do not rewrite immutable published provenance, recycle IDs or relabel old generated assets as Blender-authored. Use explicit schema versions and compatibility readers. Mutable records may migrate through checked updates. Preserve command receipts so retries across an upgrade do not create duplicate versions.

Keep API and worker compatibility windows explicit. Reject unsafe version combinations with a reason rather than best-effort decoding of unknown fields. The migration document should include old/new workflow mapping, source-role contract changes, recovery steps and rollback limitations.

26. Final architecture verdict and completion criteria

The three-role split is appropriate because inference and interactive authoring need different hardware, operating systems, permissions and recovery behavior. The cost is a real distributed-systems surface: pairing, transfer, uncertain execution, version compatibility and source restoration. Clear ownership makes that cost manageable.

The implementation is complete for the agreed scope when a user can plan an asset, choose manual or managed MacBook authoring with either supported provider, take over safely, preserve .blend sources and dependencies, submit exact evidence, pass configurable review and deliver the approved export into a Godot test project. The backend must remain usable without model weights or connected execution machines, and multiple compute nodes must execute independently without double-counting physical resources or duplicating publication.

Non-negotiable boundary: Studio decides what is requested and accepted. A compute node decides whether it can safely execute assigned model work. The MacBook companion controls who may edit the Blender workspace. Immutable source and result records connect those responsibilities without making any worker a second product authority.
